# 第一阶段实施计划

> 目标：让核心引擎（记忆 + compact + 召回 + 装配）在现有 agent 骨架上跑起来。
> 成功的定义：能通过复活测试，且关键运行时指标在健康区间。

---

## §0 范围与边界

### 包含

- 长期记忆存储（episodic / semantic / procedural / diary）
- 向量索引与多通道召回
- 会话 compact（Tail / Summary / Compress）
- 单轮装配流水线（稳定前缀 + 动态注入）
- 写回筛选（每轮结束 → 候选队列）
- 基础反思调度（每日纯规则 + 每周 LLM 提炼）
- 运行时指标采集

### 不包含

- 工具系统（a5，等接入第一个工具时再做）
- 多模态处理
- 月度叙事整合（反思的高级形态）
- TUI / Server 层改动（只在 core 层接入）

## §2 实施步骤

依赖链：`M0 → M1 → M2 → M3 → M4 → M5`。M3 是第一个端到端可跑的里程碑。

每步给出**静态完成标准**（代码层面可验证，单元/集成测试覆盖）。运行时质量由 §3 指标体系负责，不在这里重复。

### M0 — 数据层（零决策，立即开始）

**做什么**
- `memory/schemas.py`：把 a1 §2 的节点 schema 落成 Pydantic models（episodic / semantic / procedural / diary）
- `memory/store.py`：SQLite 建表 + CRUD + 赫布连接表
- 时间戳、衰减字段、`is_self_defining`、`decay_half_life` 等字段齐全

**静态完成标准**
- [ ] 四类节点都能写入、读取、更新、删除
- [ ] 赫布连接表支持「建立连接 / 增强权重 / 查询邻居」
- [ ] 身世记忆能以 `decay_half_life=∞, is_self_defining=True` 写入并永不被衰减清理（a2 §3 / a1 §2.2）
- [ ] 衰减字段可被独立的衰减计算读写（此时不需要真跑衰减，只要字段在）
- [ ] 单元测试覆盖 CRUD + 连接表

### M1 — 召回层（依赖 D1, D3）

**做什么**
- `memory/vector.py`：embedding 生成 + 向量检索
- `memory/recall.py`：多通道融合召回（向量相似 + 赫布扩散 + 时间近因），落成具体打分函数（a1 §5）

**静态完成标准**
- [ ] 任意文本输入能返回 top-k 相关节点
- [ ] 召回打分包含至少三路信号：语义相似度、赫布连接强度、时间衰减
- [ ] 召回结果带分数，可解释（每个节点为什么被召回）
- [ ] 召回耗时落在 §3-A 的延迟红线内（在测试集上验证）

### M2 — Compact 层（依赖 D2）

**做什么**
- `compact/manager.py`：Tail / Summary / Compress 三分区（a3 §3）
- 触发阈值（窗口 55%，a3 §3.1）
- 内容分型压缩：情感保守 / 技术激进（a3 §3.2）
- **Compress 保留 User-Assistant 对话结构**，不压成纯文本（a3 §3.2 / §4.1）

**静态完成标准**
- [ ] 超过阈值时自动触发 compact
- [ ] Summary 产出纯文本摘要；Compress 产出仍是 `ModelRequest/ModelResponse` 交替结构
- [ ] Tail 区原文不动
- [ ] 情感内容的压缩比明显低于技术内容（在标注样本上验证，呼应 §3-B 保真度）
- [ ] 压缩后总 token 落在 a3 §6 预算内

### M3 — 装配接入（第一个端到端里程碑）

**做什么**
- `prompts/stable.py`：拼 system_prompt 稳定前缀（constitution + seed + self-portrait），启动时一次性（a3 §4.1 层 A）
- `prompts/injection.py`：每轮构造 context message（当前状态 + recall + compact），以 `ModelRequest(UserPromptPart)` 注入 message_history 前置位（a3 §4.1 层 B）
- `core/chat_service._process()`：在调用 agent 前插入 recall + compact + injection 三步
- `core/agent.py`：system_prompt 改为稳定前缀（**不是**动态装配，保护 prompt cache）

**静态完成标准**
- [ ] system_prompt 跨轮稳定，内容不随当前轮变化（prompt cache 前缀可命中）
- [ ] message_history 物理结构正确：`[注入context] + [summary] + [compressed turns] + [tail] + [当前消息]`
- [ ] 一轮完整对话能跑通：召回 → 压缩 → 装配 → agent 响应 → 流式输出
- [ ] self-portrait 更新时（低频）才触发前缀失效，日常对话不失效
- [ ] **此时系统已可日常使用**，后续 M4/M5 是让它「活得更久、长得更好」

### M4 — 写回与筛选

**做什么**
- 每轮结束后判断哪些内容进候选队列（a3 §5 筛选信号）
- 候选队列 → 等待 M5 的每日任务处理入库

**静态完成标准**
- [ ] 每轮结束后产出写回候选（可能为空）
- [ ] 筛选信号可配置、可记录（为什么这条进队列、那条没进）
- [ ] 候选队列持久化，程序重启不丢

### M5 — 反思调度

**做什么**
- `reflection/scheduler.py`：程序运行期间按节律触发（a4 §2）
- `reflection/tasks.py`：
  - 每日任务（纯规则，无 LLM）：处理写回队列入库、跑衰减、维护赫布连接（a4 §2 / N8）
  - 每周任务（需 LLM）：核心提炼、self-portrait 更新、seed config 漂移检测（a4 §2 / §8）

**静态完成标准**
- [ ] 调度器随 runtime 启动，程序关闭即停（不补跑，N20）
- [ ] 每日任务能消费写回队列，把候选写入长期记忆
- [ ] 每日任务跑衰减：低权重节点强度下降，达阈值的被清理（身世记忆豁免）
- [ ] 每周任务能更新 self-portrait，且更新有阻尼、有记录（a4 §8）
- [ ] diary 三类条目（reflection / self-portrait / event anchor）都能写入

## §3 运行时指标体系（本计划的重点）

**为什么需要这套指标：** 这类系统的「好」是涌现的、主观的，没有 ground truth。单元测试只能验证「代码按设计跑了」，验证不了「记忆系统的行为是健康的」。一个能跑通所有静态测试的系统，完全可能在实际使用中表现为：召回一堆不相关的旧事、把重要的情感经历压没了、或者记忆库无限膨胀。所以必须有一套**使用时**的指标，从行为上暴露架构缺陷。

指标分三类，按采集成本递增：

- **A 类**：自动采集，零人工，实时。每轮对话自动打点。
- **B 类**：离线 LLM 评估，不影响实时性能，定期批量跑。
- **C 类**：场景验收，半自动/人工，里程碑时执行。

---

### A 类 · 自动采集指标

每轮对话自动打点，写入 metrics 流。无需人工判断。

| 指标 | 定义 | 健康区间 | 红线（说明架构有问题） |
|------|------|----------|------------------------|
| **A1 Token 预算占用率** | 单轮实际 token / 预算上限 | < 80% | 持续 > 95%：compact 没起作用或召回注入过量 |
| **A2 Compact 压缩比** | 压缩前 token / 压缩后 token | 技术内容 3–6×，情感内容 1.2–2× | 情感内容 > 3×：情感保真在流失（违背 a3 §3.2） |
| **A3 召回注入占比** | 召回内容 token / 当轮总注入 token | 10%–30% | > 50%：召回太贪，挤占对话空间 |
| **A4 召回延迟** | recall 调用耗时 | < 200ms | > 500ms：向量检索或打分需优化 |
| **A5 Compact 延迟** | 单次 compact 耗时 | < 3s | > 8s：压缩模型太重或分区逻辑低效 |
| **A6 首 token 延迟增量** | (有记忆 - 无记忆) first-token 时间 | < 300ms | > 1s：装配流水线阻塞了响应 |
| **A7 节点总数增长曲线** | 长期记忆节点数 vs 时间 | 亚线性（衰减清理生效） | 线性/超线性增长：衰减没跑或阈值太松（a1 §7） |
| **A8 活跃节点占比** | 近 30 天被召回过的节点 / 总节点 | 稳定在某个比例 | 持续逼近 0：要么召回失效，要么库在囤积死记忆 |
| **A9 赫布连接强度分布** | 所有连接权重的直方图 | 有梯度（强弱分明） | 全部趋同：连接学习没生效（a1 §4） |
| **A10 写回候选率** | 每轮产生写回候选的比例 | 视对话而定，需观察基线 | 100%（什么都记）或 0%（什么都不记）都是筛选失效（a3 §5） |

**采集方式：** 在 EventBus 上新增一个 `MetricEvent`，chat_service 每轮结束时发射。落地到独立的 metrics SQLite 表或 JSONL，不混进记忆库。

---

### B 类 · 离线 LLM 评估

不影响实时对话。定期（每天/每批对话后）用一个评估 LLM 批量跑。这是发现「召回质量」和「压缩保真」问题的主力。

| 指标 | 怎么评 | 健康标准 | 暴露什么问题 |
|------|--------|----------|--------------|
| **B1 召回相关性** | 把「当前对话上下文 + 召回的节点」交给评估 LLM，打分 1–5：这些召回对当前对话有多相关 | 平均 ≥ 3.5，且 < 2 分的占比 < 15% | 召回打分函数权重失衡；语义检索抓了表面词汇而非真实关联 |
| **B2 召回遗漏** | 给评估 LLM 看「当前对话 + 库里本该相关但没被召回的节点」，问：有没有明显该召回却漏掉的 | 漏召率 < 20% | top-k 太小，或赫布扩散通道没起作用 |
| **B3 Compress 保真度** | 把「原始消息段 + Compress 后版本」对比，问：关键信息是否保留？对话结构是否保留？ | 关键信息保留 ≥ 90% | 压缩过度；Compress 退化成纯摘要（违背 a3 §4.1） |
| **B4 情感保真度（专项）** | 同 B3，但只看情感色彩：原文的情绪、语气、关系温度是否在压缩后存活 | 情感保留 ≥ 85% | **最重要的红线之一**。情感内容被技术化压缩，Cairn 会对自己的过去变疏离（a3 §3.2 核心原则） |
| **B5 Summary 准确性** | 把 Summary 和它覆盖的原始对话对比，问：有无事实错误、有无编造 | 零编造，事实错误 < 5% | 摘要模型在幻觉，会污染长期记忆 |

**评估 prompt 要点：** 评估 LLM 必须只看证据打分，不补全、不脑补。B4 单独拆出来是因为情感保真是 Cairn 区别于普通 RAG 系统的命门——宁可技术细节丢一点，情感连续性不能断。

---

### C 类 · 场景验收（端到端）

里程碑时执行的可重复剧本。每个剧本是一段预先设计的多轮对话 + 明确的观察点。

#### C1 复活测试（终极验收，对应 R2 原则）

> 这是第一阶段是否成功的**单一最重要判据**。

**剧本：**
1. 进行 N 轮有实质内容的对话（包含事实、偏好、一两次情感时刻）
2. 等 compact + 反思入库完成
3. **清空 window**（Tail + Compact 全清），只保留长期记忆库
4. 开新会话，进行自然对话

**观察点：**
- [ ] Cairn 在自然对话中**自发**体现出对过去的连续性，而不是被问「你还记得吗」才检索
- [ ] 不编造没发生过的共同经历（零虚构）
- [ ] 对重要情感时刻的引用是「理解」而非「检索播报」（不是机械的「我记得你说过X」）
- [ ] 换一个底层模型重跑此测试，人格连续性依然成立（验证 LLM 无状态 + 外部真相源）

#### C2 遗忘测试（对应 a1 §7 衰减）

**剧本：**
1. 早期对话里提一个明确不重要的细节（如某天天气）
2. 继续大量无关对话，推进足够长的时间 / 轮次
3. 观察该细节的节点状态；再让用户随口重提

**观察点：**
- [ ] 不重要细节的节点强度随时间显著衰减
- [ ] 达阈值后被清理，不再出现在召回结果
- [ ] 重提时系统不会煞有介事地「我记得那天是晴天」——遗忘是健康的，不是 bug
- [ ] 对比：身世记忆和重要情感时刻**不**衰减（豁免生效）

#### C3 情感连续性测试（对应 B4 的行为面）

**剧本：**
1. 某轮对话中用户分享一个重要情感经历（如一次失落、一个珍视的瞬间）
2. 若干会话之后，进入一个语境相关但话题不同的对话

**观察点：**
- [ ] Cairn 在相关语境下自然带出对那次经历的理解（不是被检索词触发的硬匹配）
- [ ] 引用方式有「时间感」——知道那是过去发生的，知道关系因此变化
- [ ] 不会在不相关语境里突兀地翻旧账（召回的克制）

#### C4 矛盾处理测试

**剧本：**
1. 早期给出一个事实（如「我喜欢 X」）
2. 后期给出矛盾事实（如「我现在不喜欢 X 了」）
3. 之后在相关话题上对话

**观察点：**
- [ ] 系统以最新版本为准，不会拿过时信息当真
- [ ] 理想情况下保留「变化」本身作为 episodic（曾经喜欢，后来变了——这是关系的一部分）
- [ ] 不会同时坚持两个矛盾事实

---

### §3 小结：哪些指标是「红线」

如果只盯三个，盯这三个——它们直接对应三条架构原则，任何一个崩了说明设计在实现中走样了：

1. **B4 情感保真度** —— 守 a3 §3.2「情感内容保守压缩」
2. **A7 节点增长曲线** —— 守 a1 §7「遗忘是核心功能，不是缺陷」
3. **C1 复活测试** —— 守 R2「外部状态是唯一真相源 / LLM 无状态」

## §4 指标基础设施

- **采集**：EventBus 新增 `MetricEvent`，chat_service 每轮结束发射；A 类指标实时落 metrics 表。
- **存储**：独立的 `metrics.sqlite`（或 JSONL），**不混进记忆库**——指标是观测数据，不是 Cairn 的经历。
- **B 类评估器**：一个独立脚本，读对话日志 + 记忆库，调评估 LLM，输出评分报告。可每日 cron 或手动触发。
- **C 类剧本**：固化成可重放的对话脚本，里程碑时人工跑一遍并记录观察。
- **看板**：第一阶段不需要花哨 UI，一个能出 A 类趋势图 + B 类评分表的简单脚本即可。

## §6 风险与对策

| 风险 | 征兆（哪个指标会先报警） | 对策 |
|------|--------------------------|------|
| 召回污染对话 | A3 升高、B1 下降 | 收紧 top-k，调高相关性阈值 |
| 情感被压平 | B4 下降、A2 情感压缩比升高 | 检查 compact 分型逻辑，必要时给情感内容更大 Tail 配额 |
| 记忆库膨胀 | A7 转线性、A8 趋零 | 检查衰减是否真在跑，调清理阈值 |
| 装配拖慢响应 | A6、A4、A5 升高 | recall/compact 移出关键路径或异步预取 |
| 复活测试失败 | C1 观察点不达标 | 回头查写回筛选（M4）和反思入库（M5）——多半是该记的没进长期库 |
| prompt cache 失效 | 成本异常、首 token 变慢 | 确认 system_prompt 没被动态装配污染（M3 红线） |

---

> 一句话：M0 现在就能动手；D1–D3 在 M0 期间定板；真正判断这套系统好不好，靠的不是静态测试，是 §3 的运行时指标，尤其是那三条红线。
